# v0.2 — lazy subscriptions

## Motivation

Today the live backend subscribes (via `subscribe_raw`) to **every** topic it
discovers on the ROS graph, and decodes every sample on every topic (since
v0.1.x via `WrappedNativeMsgUntyped`). That's wasteful in two ways:

- **Bandwidth and CPU on the rostop side.** A graph with a 30 Hz RGB image
  and a 30 Hz `PointCloud2` is delivering tens of MB/s into the rostop
  process even when the user is staring at `/cmd_vel`.
- **Observable side-effects on the robot.** Subscribing to a topic forces
  publishers to keep that history queue alive and, in some cases, emits
  warnings (`Subscription to deprecated ~/state topic. Use ~/controller_state
  instead.` from `joint_trajectory_controller` is the motivating example).
  rostop is supposed to be a passive inspector; right now it isn't.

The inspector only ever looks at **one** topic at a time. v0.2 changes the
live backend to match that: subscribe lazily, only to the currently-focused
topic.

## Target behaviour

- On startup, rostop discovers the graph as today (`get_topic_names_and_types`
  + `get_publishers_info_by_topic`) and emits `BackendEvent::Topic { … }`
  rows for the table. **No `subscribe_raw` calls.**
- The TUI tracks which topic is "focused" (the row under the cursor in the
  table; this is already `App::selected`). When the focus moves, the UI tells
  the backend: *"subscribe to X, drop everything else."*
- The backend opens exactly one live subscription at a time. Samples on that
  subscription flow through the existing `BackendEvent::Sample` path —
  bytes for Hz/BW/jitter, decoded `DynamicValue` for the inspector.
- Topic discovery keeps polling on the existing 500 ms cadence so the table
  stays current.

## Touch points

### `RosBackend` trait (`crates/rostop-cli/src/backend.rs`)

Add one method:

```rust
fn set_focus(&mut self, topic: Option<&str>);
```

`None` means "no topic selected — don't subscribe to anything." Implementing
backends can ignore it (the demo backend will), but the live backend acts on
it.

### `LiveBackend` (`crates/rostop-cli/src/backend/live.rs`)

- Drop the per-topic `spawn_local` that runs during graph poll. The poll
  becomes pure discovery (Topic / TopicRemoved events only).
- Hold a `current_focus: Option<(String, SubscriptionHandle)>` on the
  spin-thread side. `SubscriptionHandle` wraps the r2r stream + an
  abort/drop signal so the previous subscription is cancelled cleanly when
  focus changes. r2r 0.9 streams stop on drop, so a `Drop` is enough; no
  explicit cancellation channel needed.
- Add a `focus_rx: Receiver<Option<String>>` plumbed in from `LiveBackend::set_focus`.
  Drained at the top of each spin tick.
- When a new focus arrives:
  1. Drop the previous handle.
  2. Look up the type from the discovery cache (the existing `known: HashMap`).
  3. `subscribe_raw` + build a `WrappedNativeMsgUntyped` decoder for that one
     topic.
  4. Spawn the forwarder future as today.

### App / UI (`crates/rostop-cli/src/app.rs`, `crates/rostop-cli/src/ui/*`)

- After every input that can move the selected row (`j` / `k` / `g` / `G`,
  filter narrowing, sort that reshuffles), call
  `app.backend.set_focus(Some(name))`.
- When the table becomes empty (nothing matches the filter), call
  `set_focus(None)`.
- The Hz / BW / Jit / P/S columns become **only meaningful for the focused
  row.** Unfocused rows show `—` for Hz/BW/Jit and still show the static
  fields (type, publisher / subscriber count). The sparkline pane already
  only renders the selected topic, so it doesn't change.

### Peer probe (`spin_loop`, `peer_mismatch_error`)

The current probe waits 2 s for *any* sample across all auto-subscriptions
and bails with a distro-mismatch hint if none arrive. With lazy subs there
are no auto-subscriptions and the probe can't run as designed.

Replace it with a **first-focus probe**: the first time the user lands on a
foreign-published topic, give the subscription 2 s to deliver a sample; if
not, surface the same distro/RMW-mismatch hint as a non-fatal toast in the
status bar (not an `Err` returned from `LiveBackend::new`). This keeps
rostop launchable on an empty graph, on transient-local-only graphs, and
when the user is using rostop precisely *because* the data plane is broken
and they want to see the topic list.

`ROSTOP_SKIP_PEER_PROBE` becomes obsolete; remove it.

## Demo backend

`DemoBackend::set_focus` is a no-op. The demo backend keeps emitting
samples for all its fake topics — its job is to make rostop *look* alive
without a ROS install, and the laziness change is purely a live-backend
concern.

## Tests

- `live::tests::set_focus_starts_one_subscription` — assert that
  `LiveBackend::new()` followed by `set_focus(Some("/topic"))` reaches a
  Sample event, and `set_focus(None)` stops them.
- `live::tests::changing_focus_drops_previous_subscription` — subscribe to
  topic A (assert samples flowing), `set_focus(Some(B))`, assert A samples
  stop and B samples start.
- `app::tests::moving_selection_updates_backend_focus` — a fake backend
  that records `set_focus` calls; assert it's called with the row name
  every time `selected` changes.

## Tradeoffs

- The table loses live Hz/BW/Jit columns for unfocused rows. That's a real
  regression in "scan the whole bus at a glance" usability. We accept it
  in v0.2 because (a) the v0.1 behaviour silently pays a heavy cost the
  user didn't ask for, and (b) the columns can be repopulated by adopting
  ROS 2 statistics topics later, without re-subscribing to data.
- A user that wants the v0.1 "subscribe everything" model can still get
  it via a future flag (e.g. `--firehose`); not in scope for v0.2.

## Out of scope for v0.2

- ROS 2 statistics-topic integration (`/statistics`) to repopulate the
  per-row Hz/BW columns without data subscriptions.
- Persistent multi-topic focus ("pin this topic so it keeps streaming
  even when I move the cursor"). Useful, but the design above is the
  pre-requisite.
- QoS negotiation. Still using `QosProfile::default()`.

## Acceptance criteria

1. Running rostop against the motivating graph (with
   `/joint_trajectory_controller_right/state`) and parking the cursor on
   any other topic produces **zero** deprecation warnings on the robot
   side.
2. Running rostop against a graph with a 30 Hz RGB image stream and
   focusing on `/cmd_vel` keeps rostop's RSS flat and CPU low — no image
   bytes flowing into the process.
3. Switching the cursor to the image topic starts decoding and rendering
   its fields within ~1 s; switching away stops it within the same.
4. `cargo test --workspace --features live` passes including the three
   new tests above.
